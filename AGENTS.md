# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, and others) when working with code in this repository. `CLAUDE.md` is a symlink to this file - edit this one.

## What this is

idempotency4j is a Java idempotency library published to Maven Central: clients send an `Idempotency-Key` header, and duplicate requests normally get the stored response replayed without rerunning the annotated endpoint. Same key with a different request body is rejected (fingerprint mismatch). A record is identified by an `IdempotencyIdentity(scope, key)`, never by the key alone: the HTTP filter scopes by handler method (`PaymentController.create`), so the same key sent to two endpoints is two records. Storage is pluggable (JDBC, Redis, in-memory); the Spring integration is Servlet-only (no WebFlux). The library is not by itself an exactly-once guarantee for arbitrary downstream side effects.

## Verification

Before claiming any work is done, run:

```bash
./mvnw spotless:apply   # auto-fix formatting and license headers
./mvnw verify           # compile, all tests, Spotless check
```

`verify` includes the Spotless check and is the same command CI runs - if it passes locally, CI passes. JDBC and Redis provider tests use Testcontainers (MySQL, PostgreSQL, Redis), so Docker must be running.

Requires Java 21 (see `.sdkmanrc`) and always use the Maven wrapper `./mvnw`.

## Common commands

```bash
./mvnw test -pl idempotency-core -am                  # one module's tests
./mvnw test -pl providers/idempotency-jdbc -am        # JDBC provider (needs Docker)
./mvnw test -pl providers/idempotency-redis -am       # Redis provider (needs Docker)
./mvnw test -pl idempotency-core -am -Dtest=IdempotencyEngineTest            # one class
./mvnw test -pl idempotency-core -am -Dtest='IdempotencyEngineTest#When_*'   # one test
```

Always pass `-am` with `-pl` so upstream SNAPSHOT modules build from source.

## Architecture

Four layers with strict responsibility boundaries (documented in `IdempotencyEngine` and `IdempotencyStore` Javadoc - read those before touching the lifecycle):

- **Engine** (`idempotency-core`): transport- and framework-agnostic orchestrator that owns the entire lifecycle - no HTTP types live here, so non-HTTP callers drive it directly. `execute(ctx, ThrowingSupplier<T>, PayloadCodec<T>)` calls `tryAcquire`, runs the action with a lease-extending heartbeat (fires at leaseDuration/2), encodes the result, calls `store.complete`, and fires the lifecycle callbacks around all of it; `execute(ctx, ThrowingRunnable)` is the same for an action with nothing to replay. It calls `release` on any `Throwable` from the action, but never after a completion failure - the work happened, so the record must not be erased. There is no public `complete`: an adapter cannot hold a lease. The return is a sealed `Outcome<T>`: `Executed(value)`, `Replayed(value, completedAt)`, `InFlight(retryAfter)`.
- **Completion modes**: `CompletionMode` on the context decides when the record becomes durable; an operation that does not choose gets `IdempotencyConfig.defaultCompletionMode()` (`idempotency.completion-mode`), resolved by the adapter, never by the engine. `AUTONOMOUS` (default) records the completion on its own the moment the action returns; `JOIN_TRANSACTION` has the engine call `store.complete` inside the transaction the action is already running in, so the inbox record and the business writes commit together and a crash between them leaves neither. Joined mode needs an active transaction at `execute` entry (`IllegalStateException` otherwise, checked before the lease is acquired) and a store whose `supportsTransactionalCompletion()` is `true`. The engine sees the transaction through `TransactionParticipation` (`active()`, `afterCommit`, `afterRollback`), a core interface with no transaction-API dependency, supplied as the engine's fifth constructor argument and defaulting to `TransactionParticipation.none()`; handing a real one to a store that cannot support it is an `IllegalArgumentException` at construction. In joined mode the terminal callback moves with the record: `onCompleted` fires after the commit, and a rollback releases the lease and fires `onFailed(..., ROLLBACK)`. Exactly one terminal still fires per lease, just later. Which stores support what: JDBC yes, in-memory no, Redis no and never will.
- **Completion failures**: `CompletionFailurePolicy` on `IdempotencyConfig` (the only thing the engine reads from that class - `defaultCompletionMode` and the durations are for adapters) decides what happens when the action succeeded but the store refused the completion. `PROPAGATE` (default) rethrows; `LOG_AND_RETURN` logs at error and returns `Executed` anyway. An encoding failure counts as a completion failure. Either way `onFailed(..., COMPLETION)` fires, so the one-terminal-per-lease invariant holds.
- **Spring integration** (`spring/idempotency-spring`): everything Spring but not HTTP. `SpringTransactionParticipation` reads `TransactionSynchronizationManager` so the engine can join a `@Transactional` method's transaction, and `TransactionAwareConnectionResolver` gives the JDBC store the caller's connection for `COMPLETE` and a fresh one for everything else. The transport-neutral `@Idempotent(key, scope, ttl, lease, waitTimeout, completion, codec)` lives here: `key` is a SpEL expression over the method's parameters (`#event.id()`), an empty `scope` means `<simple class name>.<method name>`, and `codec` names a `PayloadCodec` bean, required for a method that returns a value and rejected for a `void` one - this module does not serialise anything itself. Every attribute except `key` and `scope` is a string whose empty value means "use the `IdempotencyConfig` default", `completion` included (`"autonomous"` / `"join-transaction"`, case-insensitive, `-` and `_` interchangeable, unrecognised values rejected at startup) - an enum attribute could not express "unset". `IdempotentAdvisor` matches annotated methods and, because Spring consults a pointcut while it builds proxies, resolves and validates each one at startup into an `IdempotentOperation`; `IdempotentMethodInterceptor` then builds the context and runs the body through the engine. `OutcomeMapper` turns the `Outcome` back into a return value: a value for `Executed` and `Replayed` alike, and `IdempotencyInFlightException` (carrying `retryAfter`) for `InFlight`, so a broker redelivers rather than a consumer thread blocking. Joined completion needs the transaction advisor ordered ahead of `IdempotentAdvisor`.
- **Adapter** (`spring/idempotency-spring-web`): the filter and the Servlet translation, nothing else - the annotation it reads is the transport-neutral one from `idempotency-spring`, and `IdempotentHandlerRegistry` takes only the durations and the scope from it, because an HTTP request brings its own key. `IdempotencyFilter` builds the context (scope from `IdempotentHandlerRegistry`, key from the header), hands the engine a supplier that runs the chain into a `ContentCachingResponseWrapper` and returns the captured `StoredResponse`, then switches on the `Outcome`: `Executed` flushes the buffered body (so the record is durable before the client sees anything), `Replayed` writes the stored response with `Idempotent-Replayed: true`, `InFlight` answers `WebIdempotencyConfig.inFlightStatus()` (409 by default) with `Retry-After` in whole seconds, rounded up, minimum 1. Servlet translation (capture, replay, error bodies) lives in `HttpIdempotencyMapper`; HTTP-only settings live in `WebIdempotencyConfig` and `ResponseSanitizer`, including `required` - whether an unkeyed request is rejected with 422 is one answer for the whole API, not a per-endpoint one. Fingerprint mismatch is the one exception it still catches -> 422. The starter configures its engine with `LOG_AND_RETURN` (`idempotency.completion-failure-policy`).
- **Store** (`providers/*`): implements the `IdempotencyStore` SPI. The JDBC store routes every connection through a `ConnectionResolver` (`ACQUIRE`, `COMPLETE`, `RELEASE`, `EXTEND`, `PURGE`) - the resolver decides, the store obeys. Only `COMPLETE` is ever expected to get a transaction-bound connection; the store hands every connection back through `ConnectionResolver.release` rather than closing it, so it never closes or commits a connection it did not open. Without a resolver it opens a fresh autocommit connection per operation, exactly as before. All blocking, waiting, and stale-lease stealing happens inside `tryAcquire` - the engine never polls or retries. `tryAcquire` blocks for at most the context's `waitTimeout` (zero means do not block) and reports `AcquireResult.InFlight(retryAfter)` when it gives up, where `retryAfter` is the holder's remaining lease.
- **Starter** (`spring/idempotency-spring-boot-starter`): five autoconfigurations, each conditional on its own trigger so nothing activates that the application has no use for. `IdempotencyStoreAutoConfiguration` runs first and builds the store: a `JdbcIdempotencyStore` when `idempotency-jdbc` and a single `DataSource` are both present (wired with `TransactionAwareConnectionResolver`, which is what makes joined completion work without the application knowing the resolver exists), an `InMemoryIdempotencyStore` only on an explicit `idempotency.store-type=in-memory`, and never a Redis store - `RedisIdempotencyStore` needs a raw Lettuce `StatefulRedisConnection<String, byte[]>`, not the `RedisConnectionFactory` Boot produces. `store-type` is `auto` (JDBC or nothing), `jdbc`, `in-memory`, or `none`; `auto` deliberately never falls back to in-memory, because an inbox that forgets on restart must not be acquired by accident. A `SmartInitializingSingleton` logs which store was selected, fails the context when `store-type` named a backend that could not be built, and warns when nothing was. `IdempotencyAutoConfiguration` is transport-neutral: `IdempotencyConfig`, the heartbeat scheduler, the `TransactionParticipation` (a `SpringTransactionParticipation` when the store supports transactional completion, or when the application asked for joined completion and is therefore owed the engine's `IllegalArgumentException` explaining why it cannot work), and the engine. `IdempotencyWebAutoConfiguration` adds the filter under `@ConditionalOnWebApplication(SERVLET)` plus Spring MVC on the classpath; `IdempotencyMethodAutoConfiguration` adds the interceptor and advisor under Spring AOP, after `AopAutoConfiguration` whose auto-proxy creator applies the advisor; `IdempotencyPurgeAutoConfiguration` registers the purge cron. Properties live under `idempotency`, with HTTP-only ones under `web` and JDBC-only ones under `jdbc`. `idempotency.jdbc.initialize-schema` is Boot's `DatabaseInitializationMode` and defaults to `EMBEDDED`, matching what Boot does for Session and Quartz: a development H2 gets its table, a real database never gets DDL from a library.

Record state machine (in `IdempotencyStore` Javadoc), per identity: a record is absent, IN_PROGRESS, or COMPLETE - two states, not three. absent -> IN_PROGRESS -> COMPLETE, and IN_PROGRESS -> absent on error, because `release` deletes the record: a failed attempt leaves no trace and the next `tryAcquire` sees a key that was never used. The engine releases on any `Throwable`, `Error` included. Expired IN_PROGRESS leases are stolen atomically. Every acquisition has a lease; complete, release, and heartbeat mutations must match it to fence stale owners. `purgeExpired` deletes the records whose `expires_at` has passed and that nobody owns: an IN_PROGRESS record also needs an expired lease. The two timestamps answer different questions - `expires_at` is how long a completed record stays replayable, the lease is whether a caller still owns the key - and purge must ask both. Dropping a record whose lease is still being heartbeated would let a second caller rerun the protected action. An expired lease on its own marks a record as stealable, not as garbage. Stores key by the full identity: JDBC's primary key is `(scope, idempotency_key)`, Redis uses `<prefix>rec:<scope>:<key>`, in-memory maps by `IdempotencyIdentity`. A scope may not contain `':'` - that composition is only injective while it does not, and a key is client-controlled; keys may contain colons freely.

Completion stores a `Payload(type, body, attributes)` - a transport-neutral envelope core never interprets, with `Payload.none()` for a caller with nothing to replay. A `PayloadCodec<T>` translates an adapter's own result type to and from it: `StoredResponseCodec` in `idempotency-spring-web` stores an HTTP response as type `http/response` with status and headers in `attributes`, and applies the `ResponseSanitizer` inside `encode`. `attributes` is flat `Map<String, String>`, returned verbatim on a duplicate, and is where a non-HTTP caller puts correlation data such as outgoing publication ids. When a record completed is the store's to determine, not the caller's: it stamps `completedAt` and reports it on `AcquireResult.Duplicate` alongside the payload. The request fingerprint is optional; two acquisitions mismatch only when both carry one and they differ.

`IdempotencyLifecycleListener` observers fire synchronously on the calling thread, in registration order, and cannot affect store state, the return value, or a propagated exception. The load-bearing invariant is one terminal callback (`onCompleted` XOR `onFailed`) per acquired lease, always preceded by `onAcquired` - consumers unbind thread-local state there, so any new engine path that acquires a lease must fire the pair or fire neither. `onDuplicate` and `onInFlight` stand alone: no lease was acquired, so neither `onAcquired` nor a terminal callback accompanies them.

### Module dependency rules

Enforced by design, not tooling - do not violate them:

- `idempotency-core`: zero framework dependencies.
- `providers/*`: depend on core only, no Spring.
- `idempotency-test`: core plus JUnit. Holds both store contracts.
- `spring/idempotency-spring`: core + `spring-context`, `spring-aop`, `spring-tx`, and optionally `spring-jdbc` with `idempotency-jdbc` for the connection resolver. Transport-neutral: `grep -rn "jakarta.servlet" spring/idempotency-spring/src` must stay empty.
- `spring/idempotency-spring-web`: `idempotency-spring` + Spring Web, plus Jackson for the header map `StoredResponseCodec` carries in a payload attribute.
- `spring/idempotency-spring-boot-starter`: `idempotency-spring` and `idempotency-spring-web` required, every provider and `spring-jdbc` optional, autoconfiguration only. An optional provider dependency lets `@ConditionalOnClass` compile; it never drags a provider into an application that did not ask for one.

### The store contract

`IdempotencyStoreContract` in `idempotency-test` is the single source of truth for store behavior. Every `IdempotencyStore` implementation must extend it and pass all of it. A store whose `supportsTransactionalCompletion()` is `true` must also extend `TransactionalStoreContract`, which covers completing inside a caller's transaction: visible as a duplicate after a commit, back to IN_PROGRESS after a rollback, and never visible to another connection before the commit. The subclass supplies a store wired to a transaction plus a handle for committing or rolling it back. New store = implement the SPI, extend the contract, implement `store()`. Behavior changes to stores belong in the contract first so every backend is held to them.
