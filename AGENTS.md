# AGENTS.md

This file provides guidance to coding agents (Claude Code, Codex, and others) when working with code in this repository. `CLAUDE.md` is a symlink to this file - edit this one.

## What this is

idempotency4j is a Java idempotency library published to Maven Central: clients send an `Idempotency-Key` header, and duplicate requests normally get the stored response replayed without rerunning the annotated endpoint. Same key with a different request body is rejected (fingerprint mismatch). A record is identified by an `IdempotencyIdentity(scope, key)`, never by the key alone: the HTTP filter scopes by handler method (`PaymentController.create`), so the same key sent to two endpoints is two records. Storage is pluggable (JDBC, Redis, in-memory); the Spring integration is Servlet-only (no WebFlux). The library is not by itself an exactly-once guarantee for arbitrary downstream side effects.

## Verification

Before claiming any work is done, run:

```bash
./mvnw spotless:apply   # auto-fix formatting and license headers
./mvnw verify           # compile, all tests, Spotless check
```

`verify` includes the Spotless check and is the same command CI runs - if it passes locally, CI passes. JDBC and Redis provider tests use Testcontainers (MySQL, PostgreSQL, Redis), so Docker must be running.

Requires Java 21 (see `.sdkmanrc`) and always use the Maven wrapper `./mvnw`.

Java 21 is the compile baseline, not the only supported runtime: CI runs the build on 21 and 25,
against Spring Boot 4.0 and 4.1 (`-Dspring-boot.version=`). Develop on 21 - it is what catches
accidental use of a Java 22+ API. The Spring modules target Spring Boot 4 / Framework 7; Boot 3 is
not supported and lives on the `0.3.x` branch.

## Common commands

```bash
./mvnw test -pl idempotency-core -am                  # one module's tests
./mvnw test -pl providers/idempotency-jdbc -am        # JDBC provider (needs Docker)
./mvnw test -pl providers/idempotency-redis -am       # Redis provider (needs Docker)
./mvnw test -pl idempotency-core -am -Dtest=IdempotencyEngineTest            # one class
./mvnw test -pl idempotency-core -am -Dtest='IdempotencyEngineTest#When_*'   # one test
```

Always pass `-am` with `-pl` so upstream SNAPSHOT modules build from source.

## Architecture

Four layers with strict responsibility boundaries (documented in `IdempotencyEngine` and `IdempotencyStore` Javadoc - read those before touching the lifecycle):

- **Engine** (`idempotency-core`): transport- and framework-agnostic orchestrator that owns the entire lifecycle - no HTTP types live here, so non-HTTP callers drive it directly. `execute(ctx, ThrowingSupplier<T>, PayloadCodec<T>)` calls `tryAcquire`, runs the action with a lease-extending heartbeat (fires at leaseDuration/2), encodes the result, calls `store.complete`, and fires the lifecycle callbacks around all of it; `execute(ctx, ThrowingRunnable)` is the same for an action with nothing to replay. It calls `release` on any `Throwable` from the action, but never after a completion failure - the work happened, so the record must not be erased. There is no public `complete`: an adapter cannot hold a lease. The return is a sealed `Outcome<T>`: `Executed(value)`, `Replayed(value, completedAt)`, `InFlight(retryAfter)`.
- **Completion modes**: `CompletionMode` on the context decides when the record becomes durable; an operation that does not choose gets `IdempotencyConfig.defaultCompletionMode()` (`idempotency.completion-mode`), resolved by the adapter, never by the engine. `AUTONOMOUS` (default) records the completion on its own through `store.complete`: at once when no transaction is active as the action returns, and otherwise after that transaction commits - the heartbeat keeps running until then, `execute` returns `Executed` straight away, a rollback releases the lease, and a failure of the deferred write is logged and reported as `onFailed(..., COMPLETION)` whatever the policy, because the caller already has its answer. Recording it earlier would replay, to every later duplicate, work a rollback undid. `JOIN_TRANSACTION` has the engine call `store.completeInTransaction` inside the transaction the action is already running in, so the inbox record and the business writes commit together and a crash between them leaves neither. Joined mode needs an active transaction at `execute` entry and a store whose `supportsTransactionalCompletion()` is `true` (`IllegalStateException` otherwise, checked before the lease is acquired). The engine sees the transaction through `TransactionParticipation` (`active()`, `afterCommit`, `afterRollback`), a core interface with no transaction-API dependency, supplied as the engine's fifth constructor argument and defaulting to `TransactionParticipation.none()`, which sees no transaction; any store can be given a real one, since deferring an autonomous completion needs nothing from the store. Whenever the completion waits on a transaction, the terminal callback waits with it: `onCompleted` fires after the commit, and a rollback releases the lease and fires `onFailed(..., ROLLBACK)`. Exactly one terminal still fires per lease, just later. Which stores support what: JDBC yes, in-memory no, Redis no and never will.
- **Completion failures**: `CompletionFailurePolicy` on `IdempotencyConfig` (the only thing the engine reads from that class - `defaultCompletionMode` and the durations are for adapters) decides what happens when the action succeeded but the store refused the completion. `PROPAGATE` (default) rethrows; `LOG_AND_RETURN` logs at error and returns `Executed` anyway. An encoding failure counts as a completion failure. Either way `onFailed(..., COMPLETION)` fires, so the one-terminal-per-lease invariant holds. The policy governs autonomous completions only: a joined completion failure always propagates, because swallowing it would let the transaction commit the business writes without the record, and the engine registers an `afterRollback` that releases the lease (firing nothing - the terminal already fired) so a rolled-back key is retryable at once.
- **Spring integration** (`spring/idempotency-spring`): everything Spring but not HTTP. `SpringTransactionParticipation` reads `TransactionSynchronizationManager` so the engine can join a `@Transactional` method's transaction, and `TransactionAwareConnectionResolver` gives the JDBC store the caller's connection for `COMPLETE_IN_TRANSACTION` and a fresh one for everything else - `COMPLETE` included, because a deferred autonomous completion runs from `afterCompletion`, where Spring still has the finished transaction's connection bound. The transport-neutral `@Idempotent(key, scope, ttl, lease, waitTimeout, completion, codec)` lives here: `key` is a SpEL expression over the method's parameters (`#event.id()`), an empty `scope` means `<simple class name>.<method name>`, and `codec` names a `PayloadCodec` bean, required for a method that returns a value and rejected for a `void` one - this module does not serialise anything itself. Every attribute except `key` and `scope` is a string whose empty value means "use the `IdempotencyConfig` default", `completion` included (`"autonomous"` / `"join-transaction"`, case-insensitive, `-` and `_` interchangeable, unrecognised values rejected at startup) - an enum attribute could not express "unset". `IdempotentAdvisor` matches annotated methods and, because Spring consults a pointcut while it builds proxies, resolves and validates each one at startup into an `IdempotentOperation`; `IdempotentMethodInterceptor` then builds the context and runs the body through the engine. `OutcomeMapper` turns the `Outcome` back into a return value: a value for `Executed` and `Replayed` alike, and `IdempotencyInFlightException` (carrying `retryAfter`) for `InFlight`, so a broker redelivers rather than a consumer thread blocking. `IdempotentBeanPostProcessor` (an `AbstractBeanFactoryAwareAdvisingPostProcessor`) applies the advisor, appended behind any advice a bean already has, so the interceptor always runs inside the bean's transaction whatever order the transaction advisor has - no `@EnableTransactionManagement(order = ...)`. It takes the interceptor as a `Supplier` resolved only when the first `@Idempotent` method matches: a post-processor is created before ordinary beans, and resolving the engine, store and `DataSource` eagerly would hide them from every post-processor registered after it. `IdempotentAdvisor` refuses to be a bean (its `afterPropertiesSet` fails the context): the auto-proxy creator would apply it at an order that ties with the transaction advisor's, and next to the post-processor it would advise every method a second time. Like `@Async`, it cannot advise a bean in a circular reference.
- **Adapter** (`spring/idempotency-spring-web`): the filter and the Servlet translation, nothing else - the annotation it reads is the transport-neutral one from `idempotency-spring`, and `IdempotentHandlerRegistry` takes only the durations and the scope from it, because an HTTP request brings its own key. `IdempotencyFilter` builds the context (scope from `IdempotentHandlerRegistry`, key from the header), hands the engine a supplier that runs the chain into a `ContentCachingResponseWrapper` and returns the captured `StoredResponse`, then switches on the `Outcome`: `Executed` flushes the buffered body (so the record is durable before the client sees anything), `Replayed` writes the stored response with `Idempotent-Replayed: true`, `InFlight` answers `WebIdempotencyConfig.inFlightStatus()` (409 by default) with `Retry-After` in whole seconds, rounded up, minimum 1. Servlet translation (capture, replay, error bodies) lives in `HttpIdempotencyMapper`; HTTP-only settings live in `WebIdempotencyConfig` and `ResponseSanitizer`, including `required` - whether an unkeyed request is rejected with 422 is one answer for the whole API, not a per-endpoint one. Fingerprint mismatch is the one exception it still catches -> 422. The starter configures its engine with `LOG_AND_RETURN` (`idempotency.completion-failure-policy`).
- **Store** (`providers/*`): implements the `IdempotencyStore` SPI. The JDBC store routes every connection through a `ConnectionResolver` (`ACQUIRE`, `COMPLETE`, `RELEASE`, `EXTEND`, `PURGE`) - the resolver decides, the store obeys. Only `COMPLETE_IN_TRANSACTION` is ever expected to get a transaction-bound connection; the store hands every connection back through `ConnectionResolver.release` rather than closing it, so it never closes or commits a connection it did not open. Without a resolver it opens a fresh autocommit connection per operation, exactly as before. It resolves a `Dialect` from the database product name: MySQL and MariaDB get the MySQL schema file and read the clock with `UTC_TIMESTAMP`, PostgreSQL gets its own file and `CURRENT_TIMESTAMP AT TIME ZONE 'UTC'`, and every other database, H2 included, gets the PostgreSQL file (standard SQL) and a plain `CURRENT_TIMESTAMP`. The store contract runs on H2 as well as on the two containers, so the embedded development path stays covered. All blocking, waiting, and stale-lease stealing happens inside `tryAcquire` - the engine never polls or retries. `tryAcquire` blocks for at most the context's `waitTimeout` (zero means do not block) and reports `AcquireResult.InFlight(retryAfter)` when it gives up, where `retryAfter` is the holder's remaining lease.
- **Starter** (`spring/idempotency-spring-boot-starter`): five autoconfigurations, each conditional on its own trigger so nothing activates that the application has no use for. `IdempotencyStoreAutoConfiguration` runs first and builds the store: a `JdbcIdempotencyStore` when `idempotency-jdbc` and a single `DataSource` are both present (wired with `TransactionAwareConnectionResolver`, which is what makes joined completion work without the application knowing the resolver exists), an `InMemoryIdempotencyStore` only on an explicit `idempotency.store-type=in-memory`, and never a Redis store - `RedisIdempotencyStore` needs a raw Lettuce `StatefulRedisConnection<String, byte[]>`, not the `RedisConnectionFactory` Boot produces. `store-type` is `auto` (JDBC or nothing), `jdbc`, `in-memory`, or `none`; `auto` deliberately never falls back to in-memory, because an inbox that forgets on restart must not be acquired by accident. A `SmartInitializingSingleton` in `IdempotencyAutoConfiguration` (there rather than in the store autoconfiguration, which backs off entirely once the application declares its own store) logs which store was selected, fails the context when `store-type` named a backend that could not be built, and warns when nothing was; a second one in the JDBC branch warns after startup when `idempotency_records` cannot be queried, so a missing table is announced once rather than discovered as a 500 on the first keyed request. `IdempotencyAutoConfiguration` is transport-neutral: `IdempotencyConfig`, the heartbeat scheduler, the `TransactionParticipation` (always a `SpringTransactionParticipation`, whatever the store, because autonomous completions wait on the transaction too), and the engine. An application-wide `join-transaction` against a store that cannot support it fails the context before the engine is built, with a message that names the property rather than the engine's `TransactionParticipation` vocabulary. `IdempotencyWebAutoConfiguration` adds the filter under `@ConditionalOnWebApplication(SERVLET)` plus Spring MVC on the classpath; `IdempotencyMethodAutoConfiguration` adds the interceptor and a static `IdempotentBeanPostProcessor` bean (following `spring.aop.proxy-target-class`) under Spring AOP; `IdempotencyPurgeAutoConfiguration` registers the purge cron. Properties live under `idempotency`, with HTTP-only ones under `web` and JDBC-only ones under `jdbc`. `idempotency.jdbc.initialize-schema` is Boot's `DatabaseInitializationMode` and defaults to `EMBEDDED`, matching what Boot does for Session and Quartz: a development H2 gets its table, a real database never gets DDL from a library.

Record state machine (in `IdempotencyStore` Javadoc), per identity: a record is absent, IN_PROGRESS, or COMPLETE - two states, not three. absent -> IN_PROGRESS -> COMPLETE, and IN_PROGRESS -> absent on error, because `release` deletes the record: a failed attempt leaves no trace and the next `tryAcquire` sees a key that was never used. The engine releases on any `Throwable`, `Error` included. Expired IN_PROGRESS leases are stolen atomically. Every acquisition has a lease; complete, release, and heartbeat mutations must match it to fence stale owners. `purgeExpired` deletes the records whose `expires_at` has passed and that nobody owns: an IN_PROGRESS record also needs an expired lease. The two timestamps answer different questions - `expires_at` is how long a completed record stays replayable, the lease is whether a caller still owns the key - and purge must ask both. Dropping a record whose lease is still being heartbeated would let a second caller rerun the protected action. An expired lease on its own marks a record as stealable, not as garbage. Stores key by the full identity: JDBC's primary key is `(scope, idempotency_key)`, Redis uses `<prefix>rec:<scope>:<key>`, in-memory maps by `IdempotencyIdentity`. A scope may not contain `':'` - that composition is only injective while it does not, and a key is client-controlled; keys may contain colons freely.

Completion stores a `Payload(type, body, attributes)` - a transport-neutral envelope core never interprets, with `Payload.none()` for a caller with nothing to replay. A `PayloadCodec<T>` translates an adapter's own result type to and from it: `StoredResponseCodec` in `idempotency-spring-web` stores an HTTP response as type `http/response` with status and headers in `attributes`, and applies the `ResponseSanitizer` inside `encode`. `attributes` is flat `Map<String, String>`, returned verbatim on a duplicate, and is where a non-HTTP caller puts correlation data such as outgoing publication ids. When a record completed is the store's to determine, not the caller's: it stamps `completedAt` and reports it on `AcquireResult.Duplicate` alongside the payload. The request fingerprint is optional; two acquisitions mismatch only when both carry one and they differ.

`IdempotencyLifecycleListener` observers fire synchronously on the calling thread, in registration order, and cannot affect store state, the return value, or a propagated exception. The load-bearing invariant is one terminal callback (`onCompleted` XOR `onFailed`) per acquired lease, always preceded by `onAcquired` - consumers unbind thread-local state there, so any new engine path that acquires a lease must fire the pair or fire neither. `onDuplicate` and `onInFlight` stand alone: no lease was acquired, so neither `onAcquired` nor a terminal callback accompanies them.

### Module dependency rules

Enforced by design, not tooling - do not violate them:

- `idempotency-core`: zero framework dependencies.
- `providers/*`: depend on core only, no Spring.
- `idempotency-test`: core plus JUnit. Holds both store contracts.
- `spring/idempotency-spring`: core + `spring-context`, `spring-aop`, `spring-tx`, and optionally `spring-jdbc` with `idempotency-jdbc` for the connection resolver. Transport-neutral: `grep -rn "jakarta.servlet" spring/idempotency-spring/src` must stay empty.
- `spring/idempotency-spring-web`: `idempotency-spring` + Spring Web. No JSON library: the header map `StoredResponseCodec` carries in a payload attribute goes through core's `AttributeJson`, as do the stores' attribute columns.
- `spring/idempotency-spring-boot-starter`: `idempotency-spring` and `idempotency-spring-web` required, every provider and `spring-jdbc` optional, autoconfiguration only. An optional provider dependency lets `@ConditionalOnClass` compile; it never drags a provider into an application that did not ask for one.

### The store contract

`IdempotencyStoreContract` in `idempotency-test` is the single source of truth for store behavior. Every `IdempotencyStore` implementation must extend it and pass all of it. A store whose `supportsTransactionalCompletion()` is `true` must also extend `TransactionalStoreContract`, which covers `completeInTransaction`: visible as a duplicate after a commit, back to IN_PROGRESS after a rollback, never visible to another connection before the commit, and never holding a duplicate past its `waitTimeout` while uncommitted - plus the inverse, that a plain `complete` while a transaction is open is visible at once and survives that transaction's rollback. The subclass supplies a store wired to a transaction plus a handle for committing or rolling it back. New store = implement the SPI, extend the contract, implement `store()`. Behavior changes to stores belong in the contract first so every backend is held to them.

## Conventions

- Test naming: `When_<Context>_Expect_<Result>`.
- Formatting is Palantir Java Format via Spotless; license headers are inserted by `spotless:apply`, never by hand.
- Keep Javadoc on public API valid - release builds (`-Prelease`) run doclint and fail on malformed Javadoc.
- `CHANGELOG.md` keeps a permanent `## [Unreleased]` section; a change a library user would notice adds its line there in the same PR.

## Releasing

Releases are tag-driven and only happen when the maintainer asks. The process is the `release` skill in `.agents/skills/release/SKILL.md` (`.claude/skills/release` is a symlink to it), and the mechanics are `scripts/release.sh`: `prepare X.Y.Z` cuts the changelog, sets the README and pom versions and tags; pushing the tag runs the Release workflow, which re-checks that commit with `scripts/release.sh check` before deploying; `next X.Y.Z` reopens development. The pom on `main` always carries the next planned version as a `-SNAPSHOT`, and CI publishes that snapshot to Central on every push to `main`. Never push a tag or change the version without being asked to release.
